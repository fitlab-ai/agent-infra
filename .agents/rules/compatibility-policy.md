# 兼容性策略

本规则约束需求分析、方案、实现和审查中的兼容性决策。默认只支持当前契约；兼容是需要证据和退出条件的例外预算，不是稳健性的默认同义词。

## 什么属于兼容逻辑

以下任一行为都属于兼容逻辑：同时接受或写入新旧 schema、字段、状态或命令；保留旧别名、adapter、wrapper、shim；在运行主路径执行迁移；根据旧格式回退到另一套语义；为旧调用方维持并行事实源或测试矩阵。

以下行为本身不属于历史兼容：当前版本操作的幂等重试与崩溃恢复；平台、操作系统或权限能力的显式分支；对未知状态失败关闭并给出恢复提示；用户明确要求的多版本公共契约。不得用这些名义扩大成旧协议支持。

## 新增兼容的准入门槛

只有任务或既有公共契约明确要求兼容，并且产物同时记录以下四项证据时，才能新增或延长兼容逻辑：

1. **对象**：仍在使用旧契约的具体消费者、已发布版本或存量数据。
2. **必要性**：为何不能原子切换、一次性转换或直接失败并提示修复。
3. **期限**：兼容窗口的版本、日期或可验证终点。
4. **退出**：删除条件以及届时要删除的代码、测试和文档。

缺少任一项时，兼容属于未经授权的范围扩张：按当前契约实现；遇到旧输入时失败关闭并提供可操作提示，或在主路径之外执行一次性显式转换。

## 实现边界

- 当前契约只有一个规范写入格式和一个事实源；禁止双写、影子状态和“先试新逻辑、失败再走旧逻辑”。
- 兼容转换集中在单一边界，转换后立即进入当前模型；业务核心不得感知多个历史版本。
- 暂时保留的兼容逻辑必须在唯一兼容边界使用 `TODO(compat): Remove ... once ...` 标记要删除的对象和可验证删除条件。该 TODO 与代码同源；任务或 Issue 只用于可选排期，不作为兼容事实源或工作流门禁。
- warning 只用于主动作仍然正确且用户可重试的外围问题，不能掩盖身份、授权、数据解释或副作用正确性的不确定。
- 删除旧能力时同步删除专属 adapter、分支、fixture、测试和迁移文档；不要新增“已删除能力不存在”的反向断言。
- 不为兼容而猜测未知状态。无法唯一解释时保留原数据、停止写入并给出重建或人工修复提示。

## 生命周期阶段要求

- **分析**：区分用户明确兼容要求与模型自行推测；列出现存消费者和数据证据。没有证据时明确采用 current-only。
- **方案**：为获准兼容标出边界、唯一转换点、窗口和删除计划；不得把兼容层当作低风险默认方案。
- **实现**：只实现已批准的兼容预算，并在唯一兼容边界写入或随重构移动 `TODO(compat)`。方案未授权的旧分支不得“顺手保留”。
- **审查**：逐项核对四项准入证据、单一事实源、退出条件及就地 `TODO(compat)`。未经授权的兼容、无期限 shim、双写或主路径迁移应作为范围与维护性问题提出。

## 既有兼容逻辑

普通任务发现范围外的既有兼容逻辑时，只确保唯一边界存在 `TODO(compat)` 并记录位置和风险，不擅自删除，也不重复添加标记。专门的简化任务应先检索这些 TODO、建立消费者与存量数据视图，再按“可立即删除 → 先告警后删除 → 暂时保留”的顺序逐项处理。
